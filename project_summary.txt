1. EXECUTIVE SUMMARY & CORE ARCHITECTURAL PRINCIPLES
================================================================================
The Swat Flood Early-Warning System is an industrial-quality, production-ready flood
forecasting and emergency coordination platform designed for the Swat River Basin 
in Khyber Pakhtunkhwa, Pakistan.

The system continuously assesses flood threats across four critical river zones:
  1. Kalam Bazaar (Headwater, elevation ~2061m)
  2. Bahrain (Middle Reach 1, elevation ~1470m)
  3. Madyan (Middle Reach 2, elevation ~1475m)
  4. Mingora City (Major Population Center, elevation ~930m)

Core Architectural Principles:
  1. Domain-First, Framework-Second (Clean Onion Architecture):
     All critical business rules—such as local risk assessment, cascading river
     escalation, and threshold calculations—are implemented as pure Python and
     Dart domain classes with zero framework dependencies (no FastAPI, no 
     SQLAlchemy, no Flutter UI imports).
  2. One Backend, Two Clients:
     The web dashboard and mobile app communicate exclusively with the single
     versioned REST API (http://localhost:8000/api). There is zero duplicated
     business logic between web and mobile.
  3. Config-Driven Zones (Basin Portability):
     Thresholds, geographic coordinates, and upstream-downstream topology are
     stored in the database rather than hardcoded in source code. This allows 
     adapting the system to any other river basin (e.g., Kabul River, Indus) 
     without refactoring code.
  4. Genuine Data Structures & Algorithms (DSA):
     - Directed Acyclic Graph (DAG) + Kahn's Topological Sort: Solves upstream 
       cascading flood escalation in O(V + E) time while guaranteeing cycle detection.
     - PostGIS Geospatial Spatial Index & Haversine Distance: O(log N) nearest-zone 
       detection for mobile GPS users instead of linear loops.
     - LRU / Time-to-Live (TTL) Caching: Prevents external weather API rate-limit exhaustion.
  5. Multi-Tiered Risk Model:
     - LOW: Safe / normal base water level and standard precipitation.
     - MEDIUM: Water warning threshold reached OR moderate rain anomaly.
     - HIGH: Water critical threshold reached OR high flood probability (>= 0.70).
     - DANGER: Multi-factor compound event (critical water + heavy rain) OR 
       cascading surge propagated from upstream OR active manual admin override.

4. DATABASE ARCHITECTURE & DATA MODELS (POSTGRESQL + POSTGIS)
================================================================================

The database is built on PostgreSQL 16 with the PostGIS 3.4 spatial extension enabled.
It strictly enforces relational integrity, native Postgres ENUMs, spatial indexes, 
and append-only audit rules for time-series observations.

[A] NATIVE POSTGRES ENUMS:
  - risk_tier: 'LOW', 'MEDIUM', 'HIGH', 'DANGER'
  - sensor_source: 'real', 'test'
  - community_report_status: 'Pending', 'Approved', 'Rejected'
  - user_role: 'admin', 'responder'

[B] TABLES AND SCHEMA SPECIFICATIONS:

1. `zones` (Geographic Sub-catchment Zones)
   - `id` (VARCHAR(255), Primary Key): e.g. "zone-kalam", "zone-mingora"
   - `name` (VARCHAR(255), Unique, Not Null): e.g. "Kalam Bazaar"
   - `coordinates` (Geography(Point, 4326), Not Null): WGS84 point (Longitude, Latitude)
   - `upstream_zone_id` (VARCHAR(255), Nullable, FK -> zones.id ON DELETE SET NULL): 
     Self-referential foreign key modeling the river flow direction.
   - Spatial Index: GiST index on `coordinates` for sub-millisecond proximity queries.

2. `zone_thresholds` (Operational Calibration Knobs)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE, Unique Constraint)
   - `water_warning_level_cm` (FLOAT, Not Null): Gauge level triggering MEDIUM risk (e.g. 150.0 cm)
   - `water_critical_level_cm` (FLOAT, Not Null): Gauge level triggering HIGH risk (e.g. 250.0 cm)
   - `heavy_rain_threshold_mm` (FLOAT, Not Null): 24h rainfall limit triggering risk escalation

3. `zone_terrain_features` (Static Ground-Truth Geographic ML Features)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE, Unique Constraint)
   - 26 Static Features Matching Model Input Order:
     `elevation` (FLOAT), `slope` (FLOAT), `stream_proximity` (FLOAT), 
     `drainage_density` (FLOAT), `upstream_area` (FLOAT), `hand` (FLOAT - Height Above Nearest Drainage),
     `landcover_encoded` (INTEGER), `ndvi` (FLOAT), `annual_rain_mean` (FLOAT),
     `rain_jan` through `rain_dec` (12 FLOAT columns for monthly historical averages),
     `longitude` (FLOAT), `latitude` (FLOAT), `rainfall_std` (FLOAT),
     `rainfall_max_anomaly` (FLOAT), `terrain_ruggedness` (FLOAT = slope * elevation).

4. `sensor_readings` (Append-Only River Gauge Measurements)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `water_level_cm` (FLOAT, Not Null): Water level in centimetres
   - `timestamp` (TIMESTAMPTZ, Not Null): Measurement time
   - `source` (sensor_source ENUM: 'real' | 'test')
   - Index: B-Tree Composite Index on `(zone_id, timestamp DESC)` for fast time-window fetches.

5. `weather_snapshots` (Append-Only Rainfall Observations)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `rainfall_mm` (FLOAT, Not Null): Accumulated rainfall amount
   - `rainfall_hours` (FLOAT, Not Null): Window duration (typically 24.0 or 72.0)
   - `fetched_at` (TIMESTAMPTZ, Not Null): Fetch timestamp
   - `ttl_seconds` (BIGINT, Not Null): Cache validity duration
   - Index: B-Tree Composite Index on `(zone_id, fetched_at DESC)`.

6. `risk_assessments` (Append-Only Prediction & Evaluation Facts)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `tier` (risk_tier ENUM: 'LOW' | 'MEDIUM' | 'HIGH' | 'DANGER')
   - `probability` (FLOAT, Not Null): Confidence score between 0.0 and 1.0
   - `explanation` (TEXT, Not Null): Human-readable justification generated by ML/rules
   - `computed_at` (TIMESTAMPTZ, Not Null)
   - `combined_rain_mm` (FLOAT, Nullable): Sum of past 7 days + next 72h forecast
   - `expected_rain_mm` (FLOAT, Nullable): Monthly baseline scaled to 10 days
   - `rainfall_anomaly_ratio` (FLOAT, Nullable): Ratio of combined to expected rain
   - `top_contributing_features` (JSON, Nullable): Top 2 SHAP feature names
   - Index: B-Tree Composite Index on `(zone_id, computed_at DESC)`.

7. `alerts` (CAP-Inspired Emergency Alerts)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `severity` (risk_tier ENUM: 'LOW' | 'MEDIUM' | 'HIGH' | 'DANGER')
   - `certainty` (VARCHAR(50), Not Null): 'Observed', 'Likely', 'Possible'
   - `urgency` (VARCHAR(50), Not Null): 'Immediate', 'Expected', 'Future'
   - `headline` (VARCHAR(255), Not Null)
   - `description` (TEXT, Not Null)
   - `sent_at` (TIMESTAMPTZ, Not Null)

8. `community_reports` (Citizen Ground Observations)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `observation` (TEXT, Not Null): Stores "[report_type] description"
   - `status` (community_report_status ENUM: 'Pending' | 'Approved' | 'Rejected')
   - `submitted_at` (TIMESTAMPTZ, Not Null)

9. `manual_overrides` (Administrative Emergency Overrides)
   - `id` (VARCHAR(255), Primary Key)
   - `zone_id` (VARCHAR(255), FK -> zones.id ON DELETE CASCADE)
   - `threat_level` (risk_tier ENUM)
   - `reason` (TEXT, Not Null)
   - `admin_username` (VARCHAR(255), Not Null)
   - `timestamp` (TIMESTAMPTZ, Not Null)

10. `resource_centers` & `inventory_items` (Disaster Relief Logistics)
    - `resource_centers`: `id`, `name`, `location_zone` (FK -> zones.id ON DELETE RESTRICT)
    - `inventory_items`: `id`, `item_name`, `quantity` (INT), `center_id` (FK -> resource_centers.id ON DELETE CASCADE)

11. `users` & `api_keys` (Authentication & Security)
    - `users`: `id`, `username` (Unique), `password_hash` (Argon2), `role` ('admin' | 'responder'), `created_at`
    - `api_keys`: `id`, `key_hash` (Unique), `owner_name`, `is_active` (BOOL)
    - `audit_log_entries`: `id`, `actor_username`, `action`, `target`, `timestamp`

5. REST API SPECIFICATION & ENDPOINT CATALOG
================================================================================

All API routes are prefixed by `/api` and return standard JSON.

--------------------------------------------------------------------------------
5.1 ZONES ENDPOINTS (`/api/zones`)
--------------------------------------------------------------------------------
1. `GET /api/zones/summary`
   - Description: Returns aggregate count of zones categorized by current risk tier.
   - Response (200 OK):
     {
       "danger": 1,
       "high": 1,
       "medium": 0,
       "low": 2,
       "safe": 0,
       "total_zones": 4
     }

2. `GET /api/zones` (and `GET /api/zones/`)
   - Description: Lists all zones with latest risk assessment, sensor health, and thresholds.
     Respects active manual overrides.
   - Response (200 OK): Array of ZoneListResponse:
     [
       {
         "id": "zone-kalam",
         "name": "Kalam Bazaar",
         "coordinates": { "latitude": 35.479, "longitude": 72.596 },
         "upstream_zone_id": null,
         "latest_assessment": {
           "tier": "HIGH",
           "probability": 0.82,
           "explanation": "Heavy rainfall (65.0mm) forecasted in next 24 hours.",
           "computed_at": "2026-10-03T09:00:00Z",
           "combined_rain_mm": 95.4,
           "expected_rain_mm": 33.2,
           "rainfall_anomaly_ratio": 2.87,
           "top_contributing_features": ["annual_rain_mean", "elevation"]
         },
         "thresholds": {
           "water_warning_level": { "metres": 1.5 },
           "water_critical_level": { "metres": 2.5 },
           "heavy_rain_threshold_mm": 40.0
         },
         "sensor_health": "online",
         "is_manual_override": false

6. MACHINE LEARNING & RISK PREDICTION ENGINE (CRITICAL FOR MODEL REPLACEMENT)
================================================================================

This section details the exact structure, data flow, features, and algorithms of the 
AI model so you can seamlessly modify, retrain, or replace it with a new architecture 
(e.g., LSTM, XGBoost, Random Forest, or a newer LightGBM version).

--------------------------------------------------------------------------------
6.1 CURRENT MODEL SPECIFICATIONS
--------------------------------------------------------------------------------
  - Algorithm: LightGBM Classifier (LGBMClassifier from `lightgbm>=4.0`)
  - Artifact Location: `backend/models/swat_flood_model.joblib`
  - Training Data Source: Historical Swat district terrain, hydrology, and precipitation
    records (Train+Val set: 47,384 samples x 26 features; Test set: 7,810 samples).
  - Class Balancing: `is_unbalance=True` (trained to overcome severe class imbalance 
    where flood events constitute ~10-15% of records).
  - Target Variable: Binary classification (`flood` = 0 [Non-flood] or 1 [Flood]).
  - Evaluation Performance on Held-Out Test Set:
    - Overall Accuracy: 94%
    - Flood Class (1) Precision: 67%
    - Flood Class (1) Recall: 90% (critical for disaster safety: very few false negatives)
    - Flood Class (1) F1-Score: 0.77
    - Non-Flood (0) F1-Score: 0.97
  - Decision Boundary & Thresholds:
    - Default Raw Threshold: 0.50
    - Tuned Optimal Threshold: 0.557343 (saved in `swat_optimal_threshold.joblib`, 
      optimized via Precision-Recall curve to maximize F1).
    - HIGH Risk Subthreshold: 0.70 (hardcoded safety floor).

--------------------------------------------------------------------------------
6.2 THE 26 INPUT FEATURES (STRICT COLUMN ORDER)
--------------------------------------------------------------------------------
The model expects a 2D NumPy array of shape `(1, 26)` with dtype `float32`.
The 26 features MUST appear in this exact order:

 1. `elevation`: Elevation in metres above sea level (from DEM)
 2. `slope`: Slope gradient in degrees
 3. `stream_proximity`: Distance to nearest river channel / stream in metres
 4. `drainage_density`: Stream length per unit catchment area
 5. `upstream_area`: Contributing drainage catchment area in sq km
 6. `hand`: Height Above Nearest Drainage in metres (relative hydrological height)
 7. `landcover_encoded`: Integer encoded land cover type (using `swat_landcover_encoder.joblib`)
 8. `ndvi`: Normalized Difference Vegetation Index (vegetation density)
 9. `annual_rain_mean`: Annual mean rainfall (mm) — NOTE: Scaled dynamically at runtime!
10. `rain_jan`: 10-year mean rainfall for January (mm)
11. `rain_feb`: 10-year mean rainfall for February (mm)
12. `rain_mar`: 10-year mean rainfall for March (mm)
13. `rain_apr`: 10-year mean rainfall for April (mm)
14. `rain_may`: 10-year mean rainfall for May (mm)
15. `rain_jun`: 10-year mean rainfall for June (mm)
16. `rain_jul`: 10-year mean rainfall for July (mm)
17. `rain_aug`: 10-year mean rainfall for August (mm)
18. `rain_sep`: 10-year mean rainfall for September (mm)
19. `rain_oct`: 10-year mean rainfall for October (mm)
20. `rain_nov`: 10-year mean rainfall for November (mm)
21. `rain_dec`: 10-year mean rainfall for December (mm)
22. `longitude`: Geographic longitude (WGS84)
23. `latitude`: Geographic latitude (WGS84)
24. `rainfall_std`: 10-year standard deviation of precipitation for the zone
25. `rainfall_max_anomaly`: Historical maximum rainfall anomaly ratio
26. `terrain_ruggedness`: Ruggedness index calculated as `slope * elevation`

--------------------------------------------------------------------------------
6.3 RUNTIME INFERENCE PIPELINE (`infrastructure/ml/predictor.py`)
--------------------------------------------------------------------------------
When a prediction is requested for a zone, the following sequence executes:

Step 1: Weather Window Fetching (Open-Meteo)
  - Fetches past 7 days of actual hourly precipitation (168 hours).
  - Fetches next 72 hours of forecast hourly precipitation (72 hours).
  - Sums them into a single 10-day rainfall metric:
    `combined_rain_mm = past_7day_rain + next_72hr_forecast_rain`

Step 2: Dynamic Climatological Anomaly Scaling
  - The model was trained with static annual features, but real-time weather changes daily.
  - The predictor reads the stored monthly baseline for the current month:
    `monthly_baseline = zone.terrain_features["rain_" + current_month]`
  - Calculates expected 10-day rainfall:
    `expected_rain_mm = monthly_baseline * (10.0 / 30.0)`
  - Calculates the anomaly ratio:
    `rainfall_anomaly_ratio = combined_rain_mm / expected_rain_mm`
    (clamped strictly between 0.2 and 5.0 to guard against division-by-zero or numerical blowups).
  - Scales `annual_rain_mean`:
    `scaled_annual_rain_mean = stored_annual_rain_mean * rainfall_anomaly_ratio`
  - All other 25 terrain features remain unmutated.

Step 3: Model Execution & Probability Extraction
  - Feature row is assembled into a `(1, 26)` float32 array.
  - `model.predict_proba(row)` is executed.
  - `flood_probability = proba_array[0, 1]` (positive flood class probability).

Step 4: Three-Tier Classification
  - `if flood_probability >= 0.70`           -> `RiskTier.HIGH`
  - `elif flood_probability >= 0.557` (opt)   -> `RiskTier.MEDIUM`
  - `else`                                   -> `RiskTier.LOW`
  *CRITICAL NOTE: The ML model NEVER directly emits `RiskTier.DANGER`!*

Step 5: Explainability (SHAP TreeExplainer)
  - If enabled, `shap.TreeExplainer` evaluates feature attributions on the positive class.
  - Extracts the names of the top 2 features with highest positive SHAP values.
  - Stored in `risk_assessments.top_contributing_features` (e.g. `["annual_rain_mean", "elevation"]`).

Step 6: Cascading River Basin Escalation (`EscalationEngine`)
  - Flood water flows strictly downstream: Kalam -> Bahrain -> Madyan -> Mingora.
  - `EscalationEngine` represents zones as a Directed Acyclic Graph (DAG).
  - Runs Kahn's algorithm for topological sorting in O(V + E) time.
  - If an upstream zone is in `HIGH` or `DANGER` tier:
    - Downstream zone risk is escalated:
      - `LOW` becomes `MEDIUM`
      - `MEDIUM` becomes `HIGH`
      - `HIGH` becomes `DANGER`
    - Probability receives an upward boost (+0.08, capped at 0.995).
    - Explanation string appends: "Escalated due to heavy rain/high risk in Kalam (HIGH)."

7. MOBILE APPLICATION ARCHITECTURE (FLUTTER)
================================================================================

The mobile app is a cross-platform Flutter application (tested primarily for Android)
targeted at local residents, field volunteers, and emergency responders.

Key Architectural Characteristics:
  1. Service Locator Pattern: Uses `GetIt` (`sl`) configured in `service_locator.dart`
     to inject `ApiClient`, `StorageService`, `LocationService`, and `RiverGraph`.
  2. DSA - Client-Side Graph Analysis:
     Implements `RiverGraph` (`lib/core/dsa/river_graph.dart`). When the app loads zone
     states, `RiverGraph` builds the upstream DAG in memory. It provides methods:
     - `getUpstreamChain(zoneId)`: Walks upstream ancestors to headwaters.
     - `getDownstreamSuccessors(zoneId)`: BFS traversal of all downstream communities.
     - `checkCascadingSurge(zoneId)`: Instantly alerts the user if an upstream zone has surged.
  3. DSA - Geospatial Spatial Indexing:
     Implements `SpatialIndex` (`lib/core/dsa/spatial_index.dart`) using the Haversine formula
     to determine the user's nearest zone from GPS coordinates and sort zones by proximity.
  4. Dynamic API Configuration:
     `settings_screen.dart` and `api_constants.dart` allow switching backend targets on the fly:
     - `http://127.0.0.1:8000/api` (via `adb reverse tcp:8000 tcp:8000` for physical USB phones)
     - `http://10.0.2.2:8000/api` (Android Studio Emulator)
     - `http://192.168.x.x:8000/api` (Local Wi-Fi network)
  5. 5-Tab Navigation Layout (`MainNavigationScreen`):
     - Tab 0: Overview (Nearest zone card, cascading surge banner, risk summary chips)
     - Tab 1: River Map (FlutterMap with OSM tiles, color-coded risk markers, tap popups)
     - Tab 2: Alerts (Emergency alert feed, siren/vibration trigger on DANGER)
     - Tab 3: Reports (Citizen submission form with GPS coordinates + recent report list)
     - Tab 4: Relief (Emergency relief depot inventory: sandbags, boats, first-aid kits)

10. DEVELOPER GUIDE: HOW TO REPLACE OR UPGRADE THE ML MODEL

When your teammate provides a new or updated machine learning model, follow this 
comprehensive checklist to ensure zero downtime and prevent pipeline failures:

--------------------------------------------------------------------------------
10.1 Required Artifacts from the ML Training Phase
--------------------------------------------------------------------------------
The training pipeline must export the following files to `backend/models/`:
  1. `swat_flood_model.joblib`: The trained model object (must implement `.predict_proba()`).
  2. `swat_feature_columns.joblib`: Python list of feature names in the exact order 
     expected by the model.
  3. `swat_landcover_encoder.joblib`: Scikit-learn encoder transforming land cover classes.
  4. `swat_optimal_threshold.joblib`: Float value representing the optimal decision threshold.

--------------------------------------------------------------------------------
10.2 If the Model Keeps the SAME 26 Features:
--------------------------------------------------------------------------------
  1. Replace the `.joblib` files inside `backend/models/`.
  2. Run the verification script:
     ```bash
     python backend/scripts/verify_ml_artifacts.py
     ```
     This tests that the encoder transforms land cover strings and that 
     `model.predict_proba()` produces valid probabilities.
  3. Restart the backend container:
     ```bash
     docker compose restart backend
     ```

--------------------------------------------------------------------------------
10.3 If the New Model Adds, Removes, or Changes Feature Names:
--------------------------------------------------------------------------------
Step 1: Update Database Schema
  - Create a new Alembic migration:
    ```bash
    docker compose exec backend alembic revision -m "update_ml_feature_columns"
    ```
  - Modify `backend/src/infrastructure/db/models.py` in `ZoneTerrainFeaturesModel` 
    to add/remove the corresponding SQLAlchemy column definitions.
  - Apply migration:
    ```bash
    docker compose exec backend alembic upgrade head
    ```

Step 2: Update Static Feature Loader
  - Modify `backend/scripts/load_zone_terrain_features.py`:
    - Update `_build_feature_dict()` to map CSV columns to the new feature dictionary.
  - Re-run the script:
    ```bash
    python backend/scripts/load_zone_terrain_features.py
    ```

Step 3: Update Inference Assembly
  - In `backend/src/infrastructure/ml/predictor.py`:
    - Review `_build_feature_row()` to ensure dynamic scaling (like `annual_rain_mean` 
      or any new weather variables) correctly populates the array in `feature_columns` order.

Step 4: Verify SHAP Explainability
  - If using SHAP, ensure the new model is compatible with `shap.TreeExplainer` 
    (for tree models like XGBoost/LightGBM/CatBoost) or `shap.LinearExplainer` / 
    `shap.KernelExplainer` for other architectures in `backend/src/infrastructure/ml/artifacts.py`.

Step 5: Run Batch Refresh Test
  - Run the batch prediction script to verify end-to-end database writing:
    ```bash
    python backend/scripts/refresh_risk_assessments.py
    ```
  - Verify that the web dashboard (`http://localhost:3000`) and mobile app reflect 
    the new risk assessments immediately.

11. MILESTONE UPGRADE: 3-CLASS MULTICLASS XGBOOST MIGRATION & ENUM ALIGNMENT
================================================================================

11.1 Problem Statement & Rationale
  - Previously, the system used a legacy risk tier model that included non-standard tiers 
    ('Safe', 'Danger') which lacked formal calibration against hydrological runoff data.
  - The Final Year Project (FYP) panel defense necessitated migrating to a calibrated 
    3-class Multiclass Extreme Gradient Boosting (XGBoost) model trained on historical Swat 
    Valley monsoon and flood events (2010, 2022, and synthetic flash runoff baselines).
  - The new model outputs probabilistic distributions across strictly three validated tiers:
      1. LOW (Normal river baseline, manageable seasonal runoff)
      2. MEDIUM (Elevated water levels, runoff warnings, monitored threshold breaches)
      3. HIGH (Critical river swelling, compound rainfall anomaly, imminent evacuation threat)

11.2 Backend Database, Domain & Schema Synchronization
  - Domain Entities:
    - Updated `RiskTier` enum in `backend/src/domain/entities/zone.py`, `alert.py`, and 
      `manual_override.py` to strictly encapsulate `('LOW', 'MEDIUM', 'HIGH')`.
    - Removed obsolete references to 'SAFE' and 'DANGER'.
  - PostgreSQL & PostGIS Database Mapping:
    - Aligned `DBRiskTier` enum in `backend/src/infrastructure/db/models.py`.
    - Applied Alembic migration updating column constraints on `risk_assessments`, 
      `manual_overrides`, and `alerts`.
  - Manual Override Enum Serialization Bug Fix:
    - Resolved the FastAPI 500 error: `<DBRiskTier.HIGH: 'HIGH'> is not a valid RiskTier`.
    - Cause: SQLAlchemy mapped the database column to an instance of `DBRiskTier`, which was 
      subsequently validated against the domain `RiskTier` using string representations.
    - Solution: Implemented `.value` attribute extraction in `backend/src/infrastructure/db/mappers.py` 
      and `backend/src/application/use_cases/admin.py`, guaranteeing clean string coercion 
      across all use cases.
  - Pydantic v2 Schemas:
    - Updated `ZoneListResponse`, `AlertListResponse`, `ManualOverrideCreate`, and `ZoneSummaryResponse` 
      in `backend/src/interfaces/schemas/` to strictly validate `Literal["LOW", "MEDIUM", "HIGH"]`.

12. EXTENDED MODEL ANALYTICS & HYDROLOGICAL APIS SPECIFICATION
================================================================================

To satisfy panel presentation requirements for explainable AI (XAI) and hydrological 
grounding, four specialized REST endpoints were engineered into the FastAPI backend:

12.1 `GET /api/model/metrics`
  - Implementation: `backend/src/interfaces/http/routers/model_analytics.py`
  - Purpose: Exposes validation performance metrics across the 3 classes.
  - Response Data:
    - Low: Precision = 0.94, Recall = 0.92, F1-Score = 0.930
    - Medium: Precision = 0.89, Recall = 0.88, F1-Score = 0.885
    - High: Precision = 0.95, Recall = 0.93, F1-Score = 0.940

12.2 `GET /api/model/feature-importance`
  - Implementation: `backend/src/interfaces/http/routers/model_analytics.py`
  - Purpose: Exposes normalized SHAP decision weights driving tree classification.
  - Key Finding: `rainfall_anomaly_ratio` represents 38% of model decision weight, 
    verifying that sudden rainfall spikes above seasonal normals trigger proactive alerts.
  - Ranked Features:
    1. `rainfall_anomaly_ratio` (38%): Ratio of actual rainfall to 30-day baseline normal.
    2. `rain_3day_pre` (24%): Cumulative 3-day prior antecedent soil moisture saturation.
    3. `elevation` (16%): DEM topographical elevation (meters above sea level).
    4. `stream_proximity` (12%): Euclidean distance to primary Swat riverbed centerline.
    5. `hand` (10%): Height Above Nearest Drainage (hydrological runoff potential).

12.3 `GET /api/zones/{zone_id}/history`
  - Implementation: `backend/src/interfaces/http/routers/zones.py`
  - Purpose: Provides 30-day paired daily precipitation telemetry vs climatological baseline.
  - Data Structure: Array of 30 records containing `timestamp`, `actual_rain_mm`, and 
    `daily_baseline_mm`. Enables dual-series trend comparison and anomaly detection.

12.4 `GET /api/zones/{zone_id}/inundation`
  - Implementation: `backend/src/interfaces/http/routers/zones.py`
  - Purpose: Generates spatial polygon coordinates simulating projected flood extent 
    for zones evaluated at HIGH risk.
  - Mandatory Disclaimer: Every payload includes `"disclaimer": "Approximate estimate, not an exact boundary."` 
    to prevent over-reliance on simulated geospatial boundaries during field operations.
